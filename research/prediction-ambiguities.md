# Prediction prose decisions (fresh implementation)

Sources consulted for this module: DSC 1.1 sections 6.3–6.5, 7.4–7.6 and Annex D.2; DSC 1.2 and 1.2b section 6.4.4.1; DSC 1.1, 1.2, and 1.2a errata searched for relevant corrections; the adopted 2022 narrow-slice SCR prose. Reference-model source excerpts embedded in the 1.2a errata were not consulted. No reference-model source was consulted for this implementation.

* **Line-buffer saturation:** 1.1 §6.3 explicitly saturates the rounded stored sample to the line-buffer bit depth. §7.4 omits that saturation. The decoder uses §6.3 because §7.5 requires reconstructed prediction to match the encoder and because an overflowing rounded value cannot fit the stated storage width. This is resolved by the two normative prose sections together.
* **BP SAD equation, resolved by later erratum:** 1.1 and 1.2 §6.4.4.1 say to sum three independently clipped nine-bit partial SADs into an eleven-bit SAD, then truncate the three low bits. Their displayed equation instead clips the sum at 511 and omits truncation. DSC_v1.2a_E1 (Errata).pdf, SCR “DSC 1.2a Correct rcXformBpgOffset and bpSad to match C Model,” adopted August 3, 2017, Proposed Document Changes §6.4.4.1 (SCR page 3), expressly calls the combined clamp incorrect and directs summation followed by a three-bit shift. Its edit markup does not survive plain-text extraction accurately, but DSC 1.2b §6.4.4.1 page 88 prints the final corrected equation unambiguously. The supported future formula is `(min(partial0,511)+min(partial1,511)+min(partial2,511)) / 8`. This is now supported by normative prose and errata alone.
* **BP left-of-slice references:** the search uses vectors through −10 on blocks starting at `hPos−6`, including negative reference positions during the initial searches capable of contributing to bpCount. The inspected BP prose does not define those samples. A midpoint substitution was considered, but that analogy is not an explicit BP rule. No guessed BP execution code is shipped: the predictor constructor rejects BP requests, and the decoder rejects BP-enabled PPS as unsupported.
* **ICH width below seven:** the specification requires seven distinct previous-line positions but does not define the neighborhood when slice width is less than seven. This implementation rejects ICH neighbor references for these slices rather than inventing pixels. Predictive groups and existing history references are supported.
* **Last groups and multiple slices:** §6.5.2 explicitly excludes the last group (including a full three-pixel final group) from history updates and invalidates the shift-register history at each line when picture width differs from slice width. These requirements are implemented, and the caller must supply the multiple-slices flag.
* **Partial groups:** §7.2 produces no output beyond the slice width; §6.6 requires all three indices/residuals in entropy syntax. Predictor reconstruction processes only actual pixels and retains the rightmost actual pixel for subsequent MPP. Full-group history updates are inapplicable because the partial group is always last.

Architecture is independent: a component-major group API, two simple interleaved line arrays, and history rebuilt from a snapshot. A direct nine-pixel BP search was evaluated under Annex D.2 but removed because its boundary convention is unresolved. No reference-model structure is reproduced.

## Why the BP startup ambiguity cannot be ignored

A nine-pixel search at group start `x` includes source positions `x−6` through `x+2`; displacement −10 therefore references as far left as `x−16`. Counts can increment at x=9,12,15, making x=15 the earliest selectable BP group. Its leftmost candidate reference is still −1. At x=18 all pixel references are in range, but the consecutive-choice counter can still depend on undefined references in earlier groups. Flushing the search window does not immediately flush that counter.

Concrete counterexample, generated by direct application of the corrected specification equations (no reference code): 27 luma samples below, with both chroma components constant 256. Compare two possible absent-left conventions: component midpoint versus edge replication.

```
225 66 203 117 233 77 145 148 146 125 104 84 250 123 160 183 42 226 107 211 156 26 140 0 34 123 31
```

| Group x | Midpoint best distance / count / selected | Edge-repeat best distance / count / selected |
|---|---|---|
| 9 | 4 / 1 / MMAP | 1 / 0 / MMAP |
| 12 | 10 / 2 / MMAP | 1 / 0 / MMAP |
| 15 | 5 / 3 / BP(-5) | 5 / 1 / MMAP |
| 18 | 5 / 3 / BP(-5) | 5 / 2 / MMAP |
| 21 | 5 / 3 / BP(-5) | 5 / 3 / BP(-5) |

Groups x=15 and x=18 each contain a >32 edge, so the edge gate does not remove the difference. The counterexample establishes a real semantic dependence, not merely undefined unused reads. DSC 1.2b retains the same startup rule without specifying negative references in the inspected section. Neither the inspected 1.2/1.2a errata nor the narrow-slice SCR supplies the missing rule. BP should remain unsupported rather than silently choosing a boundary convention.

## M2 note (2026-09-23)

Block prediction is now implemented (Phase 2 of M2). The left-of-slice
question above is OQ-4 in RESEARCH.md. Both conventions discussed here,
midpoint and replication, are available through `bp_left`. Replication was
the first default, by analogy with §6.4.1's rule for previous-line samples
outside the slice. Since M2 Phase 5 the default is midpoint, the reading that
the black-box comparison with the VESA model supports (RESEARCH.md, OQ-4;
results in PROGRESS.md). `tests/discriminators/oq4_bp_left` separates the
two, and research/bp-worked-note.md works the fixtures by hand. The counterexample
above predates the M2 implementation and used its own counting details.
